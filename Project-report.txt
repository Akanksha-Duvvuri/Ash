## 1. About the project

This project presents the design and implementation of ASH, a mini Linux shell developed in C. 

The shell implements command input, argument parsing, built-in commands, process creation, program execution, input/output redirection, basic pipelines, background execution, and signal handling.

The implementation uses POSIX system calls such as `fork()`, `execvp()`, `waitpid()`, `pipe()`, `dup2()`, and `chdir()`.

## 2. Introduction

A shell is a command interpreter that provides an interface between the user and the operating system. It accepts commands, interprets them, and initiates the appropriate operations.

Linux shells such as Bash and Zsh provide extensive functionality, including scripting, process management, pipelines, and job control.

ASH implements a simplified subset of these capabilities to demonstrate how a shell interacts with operating system services.

## 3. Objectives

The objectives of this project are:

1. Develop a command-line shell using C.
2. Understand process creation and parent-child relationships.
3. Execute external Linux programs using POSIX system calls.
4. Implement process synchronization.
5. Demonstrate inter-process communication through pipes.
6. Implement input/output redirection using file descriptors.
7. Support basic foreground and background execution.
8. Explore signal handling and error management.

## 4. System Design and Architecture

The shell follows a read–parse–execute loop.

**Step 1: Input**

The shell displays a prompt and reads a command from standard input.

**Step 2: Parsing**

The input is separated into individual arguments using `strtok()`.

**Step 3: Command Identification**

The shell determines whether the entered command is built-in or requires external execution.

**Step 4: Execution**

Built-in commands are handled directly. External commands are executed by creating child processes using `fork()` and replacing the child program using `execvp()`.

**Step 5: Process Management**

Foreground commands are synchronized using `waitpid()`. Background commands allow the shell to continue accepting input.

**Step 6: Repeat**

The shell returns to the prompt until the user exits.

## 5. Implementation

### 5.1 Input Handling

The `takeInput()` function displays the shell prompt and reads the user's command using `fgets()`. The input is stored in a fixed-size character buffer.

### 5.2 Command Parsing

The `parseInput()` function uses `strtok()` to divide the command into whitespace-separated arguments. The resulting argument pointers are stored in an array terminated by `NULL`.

### 5.3 External Command Execution

The `executeCommand()` function uses `fork()` to create a child process.

The child calls `execvp()` to execute the requested program.

The parent calls `waitpid()` for foreground commands to collect the child's termination status before continuing.

### 5.4 Built-in Commands

The following commands are handled internally:

- `cd`: Changes the working directory using `chdir()`.
- `pwd`: Displays the current directory using `getcwd()`.
- `help`: Displays supported commands.
- `exit`: Terminates the shell loop.

### 5.5 Input/Output Redirection

The `handleRedirection()` function processes the operators `<`, `>`, and `>>`.

The `open()` function accesses the requested file, while `dup2()` changes the standard input or output descriptor.

The `close()` function releases descriptors that are no longer needed.

### 5.6 Inter-Process Communication

The `executePipe()` function connects two external commands using a pipe.

The first child sends its standard output into the pipe, while the second child receives the pipe data through standard input.

Both processes execute independently, with the pipe providing communication between them.

### 5.7 Background Execution

The shell supports background execution using the `&` operator.

For these commands, the parent does not perform a blocking wait immediately after creating the child.

Completed child processes are collected using `waitpid()` with `WNOHANG`.

### 5.8 Signal Handling

Basic signal handling is implemented using `sigaction()`.

The shell protects itself from Ctrl+C while allowing foreground child commands to respond to interruption.

The shell also handles child-process notifications as part of its background-process management.

## 6. Testing and Results

The shell was tested using built-in commands, external commands, file redirection, pipelines, background processes, and invalid inputs.

Successful behavior was observed for directory navigation, external command execution, input/output redirection, and single-pipe communication.

Ctrl+C was tested using a long-running `sleep` command. The foreground command was interrupted while the shell remained active and accepted subsequent commands.

Error-handling tests confirmed that missing directories, unavailable executables, missing files, and invalid pipe syntax produced diagnostic messages.

The detailed test-case document and terminal screenshots provide supporting evidence.

## 7. Limitations

The shell implements a restricted command grammar and does not provide full compatibility with Bash or Zsh.

Current limitations include no advanced quote parsing, no multiple pipelines, no command history, no complete job control, and limited combinations of redirection operators.

Background-process notifications may also interrupt the appearance of the interactive prompt.

## 8. Future Enhancements

Possible improvements include:

- Multiple chained pipelines
- Quoted and escaped argument parsing
- Command history
- Improved interactive terminal input
- More comprehensive error handling
- Job control using process groups
- Support for multiple redirection operators

## 9. Conclusion

The ASH mini shell demonstrates how a command interpreter uses operating system services to manage processes and execute programs.

Through implementing the shell, important concepts such as process creation, synchronization, file descriptors, inter-process communication, and signal management can be explored in a practical setting.

The project provides a foundation for understanding the internal operation of Unix-like command interpreters.
